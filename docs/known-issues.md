## 付款核心与内嵌结账页

### 会影响使用的

- 发 Telegram 告警时，`notify.SendText` 先同步读库解密配置，再每条消息起一个协程，不合并、不排队。告警一多（例如一个地区的单批量转人工）会拖慢付款和确认协程。Telegram 回 429 时，`Send` 已按 `retry_after` 等一下再发一次（`retry_after` 不超过 20 秒，`TestSendRetriesOnceOnRateLimit` 钉着）；超过 20 秒仍会丢。来源：PR #21 稳定性审计 G6、全项目审查 B1-06。状态：未修（429 重试已修，其余未修）。建议：一个常驻发送协程加有界队列，相同内容短时间内合并，配置缓存在内存里、设置变更时刷新。
- 确认阶段每次都新建 tls-client 并刷新会话，没有复用客户端；遇到 Cloudflare 403 会一路拖成待人工。重试退避也只用在主确认窗口，宽限延长段仍是固定间隔。来源：PR #2 Task 8 延后、PR #21 Task 12 裁定。状态：未逐条核对。
- 托管支付页（点数单）上，点击前就已显示、点击后不变的校验错误按裁定被忽略，结果是 Unknown，一单要等约 12 分钟才转待人工。（原先还有一半「提示文字的判断排在 3DS 之前」已不成立：现在 `outcome`（`page.go` 约 636–644 行）先看成功，再看 3DS 框，最后才看提示文字。）来源：PR #2 终审复审「范围外观察」、全项目审查 P2-08。状态：未逐条核对。
- `paybrowser/page.go` 的 `waitFind` 和等待页面结果时会吞掉 CDP 错误，浏览器崩溃时要等满超时才结束。来源：PR #2 Task 6 延后。状态：未逐条核对。
- `paybrowser/page.go` 的 `shotPage` 持着 `b.mu` 做 CDP 往返，截图慢时会卡住同一浏览器上的其他调用。来源：PR #2 Task 6 延后。状态：未修。
- 3DS 验证框高于视口时，截图裁掉的部分是空白。来源：PR #2 Task 6 延后。状态：未逐条核对。

## 全项目审查（2026-11-11）暂不改的项

2026-11-11 对整个仓库做了审查。下面这些问题用户决定「暂不改、记进已知问题」或「等证据再定」。每条写了现象、影响、为什么暂不改、什么时候再处理；括号里是审查编号。状态都是：未修（有意暂不改）。

### 资金与付款

- 【涉及资金】MarsWallex 时间字段遇到空字符串，整条响应解析失败（P1-04）。现象：`marswallex/types.go` 的 `Timestamp.UnmarshalJSON` 认 `null`、数字、数字字符串和 ISO 字符串，不认 `""`，返回错误后整个 `json.Unmarshal` 失败，这次 200 响应被归成「未知/decode」。另外数字 `0` 会被解析成 1970-01-01，零值时间序列化出 `-62135596800`。影响：如果平台对还没成功的转账、兑换单返回 `"success_time": ""`，查单会一直是未知，资金单据停在未知。为什么暂不改：官方文档只写「状态为 SUCCESS 时返回」，不知道平台对未成功的单实际返回缺字段、`null`、`0` 还是 `""`，资金查单的解析没有证据不动。什么时候再处理：拿到真实回复后再定（可以和「空结果是 `[]` 还是 `null`」的只读验收一起做）。建议：空字符串按 `null`、`0` 按零值处理，`MarshalJSON` 对零值输出 `0` 或 `null`。
- 【涉及资金】接口响应验签后不检查时间戳，Webhook 却检查（P1-09）。现象：`marswallex/client.go` 的 `handleResponse` 只验 `epoch&body` 的签名，不看 `epoch` 离现在多远；`ParseWebhook` 有 5 分钟窗口。影响：要先在 HTTPS 链路上截到并重放一条旧的已签名响应才能利用，现实里很难。为什么暂不改：风险低，而补上检查后平台时钟有偏差时会把正常响应归成「未知」（修复风险中），文档里秒和毫秒还混用。什么时候再处理：确认平台响应时间戳稳定、并且需要防重放时再做；做法是响应的 `epoch` 也用 `EpochTime` 解析，偏差超过窗口归「未知/signature_invalid」。
- 【涉及资金】托管页填验证码后按坐标点提交，没有落点检查（P2-10）。现象：`paybrowser/page.go` 约 829–830 行按元素中心坐标点击；内嵌页因为「验证框不一定是全屏遮罩，按坐标点会点到主页面，可能就是第二次点支付」，在 `submitOTPEmbedded` 里加了落点检查，托管页注释写明「不变」。影响：验证框里的提交按钮如果在验证框可视区外，坐标会落到主页面，理论上可能第二次点支付；托管页点过支付后主页面按钮通常处于处理中，再点不一定生效，风险比内嵌页低。为什么暂不改：没有真实托管页 3DS 的布局可验证，改了没法测。什么时候再处理：第一笔真实点数单出现 3DS 之后再定，做法是托管页也走 `submitOTPEmbedded` 的检查。
- 【涉及资金】改状态单没有「同卡在途互斥」，检查和提交之间也不是原子的（C1-12）。现象：`cardpool/admin.go` 的 `changeStatus` 先 `guardOperable` 读卡再提交，中间卡可能被租走，一张刚租出去、付款进行中的卡被冻结或注销；同一张卡也可以同时有目标相反的两张改状态单（例如回收提交的冻结单结果未知，管理员又点了解冻也超时），对账对每张 unknown 的单都会重发，卡最后停在哪个状态取决于处理顺序。影响：都要靠平台超时和并发操作才出现，只在人工操作时发生，概率低。为什么暂不改：概率低，要加部分唯一索引并改状态单的占位流程，改动面不小。什么时候再处理：下次改卡池状态单、或真的出现卡状态对不上时一起做；做法见审查 C1-12（部分唯一索引加条件更新先占住）。
- 概览页的主钱包余额只取平台返回的第一个 MAIN 账户（C1-07）。现象：`cardpool/admin.go` 的 `Overview` 只用 `page.Data[0].BalanceList`，而 `mainAccountFor` 按「平台按币种各有一个主钱包」处理。影响：商户有多个主钱包（例如 USD 和 EUR 各一个）时，概览只显示第一个的余额，只影响显示。为什么暂不改：不知道真实商户是否存在多个 MAIN 账户。什么时候再处理：确认真有多个主钱包再改；做法是概览改读本地已同步的 `mw_accounts`，或返回所有 MAIN 账户的余额。

### 数据库、停机与保留期

- 停止服务时不等后台协程结束，也不关闭数据库（B1-02）。现象：收到 SIGTERM 后，`srv.Shutdown` 排空付款引擎的在途单并关 HTTP，然后 `stopRun()` 取消 `runCtx`，`main` 立刻返回；卡池循环、CDK 维护、限流清扫、卡头同步等协程没有任何等待，`db.Close()` 全仓库没有调用方。影响：停止信号到达时卡池正好在向 MarsWallex 发请求（自动补卡、回收转出）的话，请求可能已到对方，进程却在写回结果之前退出；数据库是 WAL 加 `synchronous=FULL`，已提交的事务不会丢，不关库只是少一次收尾 checkpoint。为什么暂不改：已有崩溃恢复（对账）兜底，要改几个包的启动函数签名。什么时候再处理：对账恢复被证明恢复不了被打断的在途资金调用，或下次动停机流程时。
- 每次启动都重跑一遍只针对旧表的迁移，新装库也会建出这些没人用的表（B1-05）。现象：`createTables` 每次启动执行 `migrateCDKPlanTypes`、`migrateLegacyCDKCodes`、`migrateDefaultCardSelectionRules`、给没人读写的表补列、`MigrateWebhookPayloads`（把 `webhook_events` 全表按 500 行一批读出来比较）和对 `recharge_tasks` 的计数；新装库多出十来张空表。另外 `local_cdk.go:254` 的注释说 `recharge_tasks` 「卡密查询还在读」，与 `db.go:159` 的「代码已不读写」矛盾，前一句过时。影响：从旧版升级上来、`webhook_events` 行数多的库，每次重启和在线更新多花一段时间；新装库只是多几张空表。为什么暂不改：改迁移有风险，用户选了暂不改。什么时候再处理：确定不再接此类服务后，和删除 `cdk_session_bindings` 周边查询、清理一起一次清掉。
- 三张只增不减的表没有保留期（B1-14）。现象：`marswallex_webhook_events`（存完整原文）、`pay_order_events`、`admin_audit_logs` 全仓库没有任何 `DELETE FROM`。影响：Webhook 事件增长最快，库变大后 `VACUUM` 也会变慢；短期内没有可见影响。为什么暂不改：保留多久要用户定，付款事件和审计日志是排障和追责依据，保留期要保守。什么时候再处理：库明显变大时再定；建议已处理的 Webhook 事件留 90 天，付款事件跟随已结束很久的单据清理，审计日志是否清理由用户决定。

### 性能（等量上来再做）

- 后台码列表每次翻页都把全部本地码和全部真实付款单读进内存（H2-01）。现象：`AdminListLocalCDKs` 调 `db.LoadLocalCDKRows` 读 `local_cdks` 全表，再读 `pay_orders` 里所有 `source='cdk' AND dry_run=0` 的行来派生状态，筛选和分页都在 Go 里做，每翻一页、每换一次筛选都重复一遍。影响：代价随发码总量和付款单总量线性增长。为什么暂不改：现在码量小感觉不到，状态是派生值，不能直接下推到 SQL，改分页要小心总数。什么时候再处理：码量上万、后台页面明显变慢时；做法是套餐、服务商、代理商三个筛选下推到 SQL，只读当前页的码再读这些码的付款单，总数另用 COUNT。
- 代理商「我的码」每翻一页、每次导出、每次打开概览，都把名下全部码和它们的付款单读一遍（H1-04）。现象：`agent_codes.go` 的 `loadAgentCodes` 调 `LoadLocalCDKRowsByAgent` 加 `AgentOrderRefs`，筛选和分页在内存里做；按 ID 导出和概览数状态也先全量读。影响：单个代理商累计几万张码以后，列表、概览、导出都是几万行的读取和派生。为什么暂不改：目前量小，状态是派生的不容易下推，改查询方式牵动列表、导出、概览。什么时候再处理：单个代理商码量上万时；做法是概览和列表共用一次读取并缓存几秒，`ids` 导出改用 `LoadLocalCDKRowsByAgentIDs`，无状态筛选时把分页下推到 SQL。

### 代码整理与更新

- 批量查兑换结果在正式代码里用 gin 的测试辅助函数（H1-06）。现象：`lookup_results.go` 的 `runPublicResult` 对每个令牌调 `gin.CreateTestContext`（内部 `gin.New()`），批量页每轮轮询最多 100 个令牌就新建 100 个引擎，生产代码还引入了 `net/http/httptest`。影响：按默认 debug 模式启动时每个令牌往标准输出打 4 行 gin 警告；新引擎的受信代理是 gin 默认值而不是 `TRUSTED_PROXIES`，目前 `localCDKResult` 没用到来源 IP，所以只是隐患。线上都设了 `SERVER_MODE=release`，没有额外日志。为什么暂不改：要把 `PublicCDKResult` 拆成不依赖 `*gin.Context` 的函数，牵动 `cdk_dispatch.go`、`local_cdk.go` 的结果路径（修复风险中）。什么时候再处理：下次动结果查询时一起改。
- 命令行回滚中途失败会留下「旧程序 + 残缺前端」，`failed-*` 目录从不清理（H1-12）。现象：`selfupdate.go` 的 `rollbackWith` 先把程序换回备份，再挪走当前 web、复制备份 web；`copyDir` 中途失败（例如磁盘满）时直接返回错误，程序是旧的、web 只有一部分、`VERSION` 还是新的；在线更新的 `swapBinaryAndWeb` 做了「要么都新要么都旧」，回滚没有对等处理。每次回滚还会留下一个含程序和整份前端的 `failed-<时间>` 目录，`pruneBackups` 只管 `backup-*`。影响：触发概率低，出现时要手工修复。为什么暂不改：改顺序要补失败注入的用例，风险中。什么时候再处理：下次动在线更新时一起做；做法是回滚也按 `swapBinaryAndWeb` 的顺序，先把备份 web 复制成 `web.next`，成功后再换程序和目录，任何一步失败改名换回，并顺带只保留最近 1–2 个 `failed-*`。
- 批量兑换页等处运行时文字写死中文，英文界面下混着显示（F2-16）。现象：`BatchRedeemView.vue` 脚本里约 50 处状态、错误、导入提示，`ExcelImportBlock.vue`、`ThemeToggle.vue`、`DialogHost.vue` 的默认按钮文字等都是写死的中文，模板文字走了 `t()` 但运行中产生的文字没有。影响：切到英文后，批量页的每一行进度和所有报错仍是中文。为什么暂不改：改动面大但机械，这次不做。什么时候再处理：下次做英文界面或动批量页时；做法是把这些文字搬进 `i18n/locales` 的 `batch.*`，`DialogHost` 的默认按钮文字在用户端按当前语言取。

### 这次修复后留下的

下面是 2026-11-11 审查修复时，实现或复审发现、但判断不值得在这一轮继续改的点。状态都是：未修。

- 卡池：回收中的卡刷新失败的 30 分钟计时只存在内存里，服务重启后从头算，重启频繁时告警会晚到；两次失败隔 30 分钟以上也从头计时（C1-02）。
- 卡池：升级前已经在回收中的卡没有「进入回收的时间」，每日汇总按最后更新时间兜底；这类卡回收期间每次刷新都会更新这个时间，第一次被汇总可能比实际晚。新进入回收的卡不受影响（C1-04）。
- 卡池：判断「是不是本系统冻结的」看这张卡最近一张在途或成功的改状态单。我们冻结后，有人在平台后台手动解冻又再冻结，系统仍会当成本系统冻结、不告警（C1-06）。

## 有意不修的取舍

下面这些是有理由地决定不改，或者是用户可能碰到的已知行为限制。以后要改，先重新评估当时的理由。

- D-10：付款用的 Chrome 关闭了站点隔离（site-per-process），这是为了操作 Stripe iframe 有意为之。来源：审计 D-10。
- E-9：「售后查询对本站码换码链只解一跳」不成立：查询入口会逐层跟换码链，最多 5 层。只补了回归测试。来源：审计 E-9。
- D-3：停机时能证明没点支付的单也留在 submitted，重启后只能走人工；人工定论失败会把码标成 declined、码就作废了。按裁定不改「是否已付款」的判定，只在后台人工定论页加了提示：「如果确认这笔没有扣款，请禁用这张码后重新发码给用户」。来源：审计 D-3、裁定 R9。
- `cdk_redemption_tokens` 不设保留期、不清理（每行几十字节，旧绑定表也从不清理）。来源：裁定 R19。
- 镜像默认 `TRUSTED_PROXIES` 含整个 `172.16.0.0/12`，没改默认值，只在文档和 Dockerfile 注释里写明：不要单独 `docker run -p 8080:8080` 直接暴露端口，否则客户端能伪造来源 IP 绕过按 IP 的限流。改默认值会让容器网络里其他反代后面的所有客户端被当成同一来源。来源：审计 A-18/F-8。
- 批量兑换上限 100 张，恰好用满公开接口每 IP 每小时 300 次变更额度；同一 IP 多人共用时仍可能触顶。批量页验证和提交阶段遇到 429 显示为各条目的错误，没有页面级提示（轮询阶段有提示和退避）。来源：审计 S4 修复报告、用户决定 U2。
- 降级在线更新（目标 ≤1.5.3）照常更新，跳过 `--check`。来源：裁定 R18。
- 后台付款单列表的账号邮箱打码，详情接口、手动提交和重试关闭续费的接口返回仍带完整邮箱，给人工核对用。来源：全项目审查 H2-04、F2-20，用户决定。
- 官方发布包只有 linux/amd64，「一键更新」只认本机架构的包，arm64 机器要手动更新。来源：全项目审查 H1-07。
- 支付按钮没点到（确定没点击）时，也走 10 分钟确认、转待人工和 Telegram 告警，并用掉一次卡。方向安全，没有真实页面证据前不动资金状态机。来源：PR #2 终审 M-8、裁定 R47。
- 付款确认的几处极端时序维持现状：补拉等锁不看 ctx（`cardpool/backfill.go` 的 `backfillMu`，不会永远卡住，但超时后会把 `last_error` 写成 context deadline exceeded）；定论时的账号证据可能已过去 30 秒以上；补拉成功不等于窗口完整（窗口上界没有时钟容差，单段 200 页封顶后当作完整）。极端情况下账号刚开通却被定失败，运营可在详情里看到。来源：PR #2 终审复审、裁定 R54。
- 注资金额（美元）够不够付应付金额（本币）无法自动核对，没有汇率，由管理员按试运行价格配置。来源：PR #2 终审、裁定 R49。
- 代理商下单或调账结果不明时，请求号只存在浏览器 localStorage，换浏览器、换电脑就找不回（用户决定，CHANGELOG 已写）。来源：PR #26 用户决定。
- 代理商功能开关只管 `/api/v1/agent/*`（`/status` 除外）、`/shared/*` 和管理员代理商接口，不管老的代理换码 `/partner/swap` 和后台代理换码（用户选的）。来源：PR #29。
- 异次元签名错误按「同一商户 ID + IP 10 次锁 15 分钟、未知商户 ID 按 IP 计」实现，重置密钥或重新开通后，最长 15 分钟内仍会被拒（对接页和 CHANGELOG 有提示）。以后可以改成「签名正确即解锁」。来源：PR #28 终审裁定。
- 异次元同号重发时原样交出第一次的码，即使其中有之后被换码停用的，不改指向新码（规格 7.5「拿回第一次的码」）。下游可能发出已停用的旧码，子项目 5 自动换码时再考虑。来源：PR #28 Task 5 裁定。
- `/shared/*` 只收 HTTPS；本机直连只在请求不带任何转发头（X-Forwarded-Proto、X-Forwarded-For、Forwarded、X-Real-IP）时才豁免。同机反代没配 `TRUSTED_PROXIES` 的部署会被全部拒绝。来源：PR #28 Task 4 裁定。
- 异次元失败记录只保留 30 天，管理员端只看最近 50 条（CHANGELOG 已写）。来源：PR #28 Task 7 裁定、终审。
