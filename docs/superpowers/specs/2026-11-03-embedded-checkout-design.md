# 订阅开通支持 ChatGPT 内嵌结账页

日期：2026-11-03　状态：已定稿，实施中
前置：付款核心设计 `2026-11-01-marswallex-pay-core-design.md`（下文简称「A 设计」）、`2026-11-03-marswallex-credits-renewal-probe-design.md`（下文简称「点数设计」）

## 1. 背景

2026-11-03 实测：给没有订阅的账号建开通结账会话（`POST /backend-api/payments/checkout`，`plan_name` 为 Plus 或 Pro 任一档），ChatGPT 只返回内嵌结账会话：

- `tag` 为 `custom_checkout_session`，`checkout_ui_mode` 为 `custom`，`processor_entity` 为 `openai_llc`；
- 返回里有 `checkout_session_id`（`cs_live_…`）和 `client_secret`，**没有 `url`**；
- 请求里写明 `redirect` 或 `hosted` 也一样被改回 `custom`。

ChatGPT 网页版拿到这种返回后，打开 `https://chatgpt.com/checkout/<processor_entity>/<checkout_session_id>`。

引擎目前只认 Stripe 托管页（`pay.openai.com`、`checkout.stripe.com`），遇到没有 `url` 的返回就以「创建支付会话未返回支付链接」放弃。所以订阅开通现在全部走不通。点数单仍然返回托管页链接，不受影响。

目标：引擎能用浏览器打开这个内嵌结账页并完成付款，和用户自己在网页上开通一样。

## 2. 摸底结果

2026-11-03 在本机做了一次只读摸底：

- 出口在美国；
- 用免费号建 Pro 5x 会话；
- 用与 `paybrowser.Launch` 相同参数的 Chrome 打开内嵌页；
- 不填表、不点击。

看到的情况：

| 项 | 结果 |
|---|---|
| Cloudflare | 无界面、有界面两种模式都在 9–11 秒内打开，没有挑战页。之前免付款探测被拦，打开的是 chatgpt.com 首页，只等了 6 秒。VPS 机房 IP 会不会被拦还不知道 |
| 页面语言 | 跟账号的语言设置走（这个号是中文），不跟浏览器的 `--lang=en-US` |
| 左栏 | 档位按钮 US$100 / 200 / 500（已选中会话对应的 100）、Apple Pay、Card / PayPal 标签（默认 Card） |
| 卡片字段 | 在 `js.stripe.com` 的 iframe（Stripe Payment Element）里：`#payment-numberInput`、`#payment-expiryInput`、`#payment-cvcInput`，与 `Sel` 里已有的首选选择器一致 |
| 地址字段 | 页面上没有。国家应该由建会话时传的 `billing_details` 决定。填卡号后会不会出现国家、邮编，没有验证 |
| 保存卡勾选框 | iframe 里有 `#payment-savePaymentInput`（`name="savePayment"`），标签「Save payment details to OpenAI OpCo, LLC for future purchases」，默认没勾 |
| 金额 | 主页面右栏「今日应付金额 US$100.00」，没有 id 或 data-testid，class 都是排版用的；iframe 里有一段给读屏软件的英文「Payment amount: $100.00 Currency: usd Payment mode: Live mode…」 |
| 支付按钮 | 主页面唯一的 `button[type="submit"]`，文字随语言变（这次是「升级至 Pro」） |
| 条款 | 按钮下方的一段文字，没有勾选框 |
| 其他 iframe | OpenAI 的 sentinel（`chatgpt.com/backend-api/sentinel`）、Stripe 的隐形 hCaptcha、Apple Pay。都由页面自己在浏览器里运行，引擎不碰 |

## 3. 范围

本轮做：订阅开通（Plus、Pro 各档）在 ChatGPT 返回内嵌会话时，用浏览器打开内嵌结账页付款。

本轮**不做**：

- **点数单**：仍是托管页，保持不变；它遇到内嵌会话仍按 `custom_checkout_unsupported` 放弃。
- **已有订阅的升级**。
- **PayPal、Apple Pay**。
- **改建会话的请求体**：比如加 `checkout_ui_mode`、`entry_point`。现在不加也能拿到内嵌会话；以后发现必须加再改。
- **任何绕过 Cloudflare 或页面风控的手段**：不用伪装插件，不解人机验证，不伪造 sentinel 令牌，也不自己用 `client_secret` 拼付款页（替代方案 B、C 已否决，见 §9）。

## 4. 资金与安全约束（全部保持）

A 设计与点数设计的全部资金规则继续有效，包括：

- 注资在打开页面、读到金额之后；
- 资金单绝不自动重发；
- 先写 `submitted_at` 再点支付；
- 绝不点第二次；
- `LockSubmit` 的不点击证明；
- 开始填卡后禁止整页截图；
- 卡号、CVC、会话、邮箱一律脱敏；
- 金额上限；
- 熔断；
- 试运行不点击；
- 开通成功后关闭续费。

内嵌页带来的新约束：

- 内嵌页的所有放弃条件都在**注资之前**判定：打不开、Cloudflare、读不出金额、币种不符、超上限、低于最低金额、支付按钮不唯一。
- 金额下限（§5.10）对所有付款单生效，不只内嵌页。
- chatgpt.com 只在一种路径上放行：`/checkout/<段>/<段>`。chatgpt.com 的其他地址一律不打开。

## 5. 设计

### 5.1 流程

步骤与 A 设计相同，有改动的是建会话、打开页面、填表、等结果这四步：

```
检查账号 → 建结账会话* → 打开支付页、读金额* → 选卡注资 → 填表* → 记 submitted_at、点一次 → 等页面结果* → 查账号定论 → 关闭续费
```

### 5.2 建会话（`internal/chatgpt`）

- `Checkout` 加两个字段：`Tag`、`ProcessorEntity`。`CreateCheckout` 从返回里读出 `tag`、`processor_entity`，去掉首尾空白。
- 请求体、请求头不变。免付款探测与自动付款共用 `planCheckoutBody`，继续保持一致。
- 判定规则：
  - 返回没有 `checkout_session_id` 仍然报错，与现在一样；
  - 有 `url` 时不管 `tag` 是什么，都按托管页处理，与现在一样；
  - 没有 `url` 且 `tag` 为 `custom_checkout_session` 时，交给引擎拼内嵌页链接（§5.3）；
  - 两样都没有时，引擎照旧以 `checkout_failed`「创建支付会话未返回支付链接」放弃。

### 5.3 拼链接与白名单（`internal/payengine`）

**拼链接**（`createLink`）：

- `processor_entity` 必须匹配 `^[a-z0-9_]{1,64}$`；
- 会话号必须匹配 `^[A-Za-z0-9_]{1,255}$`；
- 任一不合格，以 `checkout_failed` 放弃，说明里不写会话号；
- 合格时拼成 `https://chatgpt.com/checkout/<processor_entity>/<会话号>`，照旧经 `acceptCheckoutURL` 校验后写入 `checkout_url`。

**白名单**（`checkCheckoutURL`）：

- 现有规则不变：
  - 必须是 https；
  - 不带账号密码；
  - 不带端口；
  - 主机名精确匹配。
- `pay.openai.com`、`checkout.stripe.com` 仍然不限路径。
- 新增 `chatgpt.com`（只认这个主机名本身，不认子域名），要求同时满足：
  - 路径正好是 `/checkout/<段>/<段>`，每段都匹配上面对应的正则；
  - 不带查询串；
  - 不带 `#` 片段。
- 不合格时以 `checkout_url_untrusted` 放弃，说明里只写域名。
- 免付款探测的 `probePayHosts` 不动。

**页面类型**：

- 新增 `checkoutPageKind(url) paybrowser.PageKind`：主机名是 `chatgpt.com` 返回 `PageEmbedded`，其余返回 `PageHosted`。
- 页面类型不落库，每次都按 `checkout_url` 现算。

### 5.4 浏览器接口（`internal/paybrowser`）

- 新增类型 `PageKind`，取值 `PageHosted`、`PageEmbedded`。
- `Open` 改为 `Open(ctx, url string, kind PageKind, cookies []Cookie) error`。页面类型记在 `Browser` 上，之后的 `WaitRendered`、`ReadAmount`、`Fill`、`PayButtonState`、`Submit`、`WaitOutcome` 都按它分支。
- `payengine.FormBrowser` 的 `Open` 签名随之更改，测试里的假浏览器一并改。
- 托管页的全部行为保持原样。下面各节只描述内嵌页。

### 5.5 内嵌页：打开

**打开**：

- 注入会话 cookie、打开链接，沿用现有逻辑。
- 在 `pageLoadTimeout`（60 秒）内等到下面三样同时成立，`Open` 才返回成功：
  - 各级 frame 里有可见的卡号框（`Sel.CardNumber`）；
  - 能读出 §5.6 的金额文字；
  - 主页面（不进 iframe）里可见的 `button[type="submit"]` 正好一个。
- 托管页不检查支付按钮，保持原样。

**打不开时**：超时后先读一次页面，按 `IsCFChallengePage` 判断是不是 Cloudflare 挑战页。

- **是挑战页**：
  - `Open` 返回包着新哨兵错误 `paybrowser.ErrCFChallenge` 的错误；
  - 引擎用 `errors.Is` 认出它，记 `cf_challenge`，并告警「请检查该地区代理的出口 IP」。
- **不是挑战页**：
  - `Open` 的错误说明写明三样里哪一样没成立，比如「找到 2 个支付按钮」；
  - 引擎照旧记 `page_failed`。
- 两种情况都发生在注资之前。

**截图**：内嵌页的 `WaitRendered` 改为等卡号框可见。

- 最多等引擎传入的 `pageRenderWait`（10 秒）。
- 等不到只记 warn，不中断。

### 5.6 内嵌页：读金额

- **来源**：在各级 frame 里找以 `Payment amount:` 开头的文字。这是 Stripe Payment Element 给读屏软件的说明，视觉上隐藏，查找时不能要求可见。
- **解析**：从所在元素的父元素的文字里，用 `Payment amount:\s*(.+?)\s+Currency:\s*([A-Za-z]{3})` 取出金额原文和币种代码。
  - `ReadAmount` 返回规范化的原文「金额里最后一段数字 + 空格 + 币种代码大写」，比如 `100.00 USD`、`1,120.00 PHP`。原来的货币符号丢掉，所以币种只由 `Currency:` 后的代码决定。
  - 引擎不改：现有的 `ParseAmount` 解析这段规范化原文；现有的 `CurrencyMatches` 比对后缀的币种代码，与单据币种不符就以 `currency_mismatch` 放弃。
  - 读不到 `Currency:` 时按读不出金额处理（`amount_unreadable`）。
- **只用这一处**：主页面右栏的「今日应付」不参与判断，因为它的文字随账号语言变，也没有稳定的 id。它只出现在开页截图里，供人工核对。
- **复读**：填表后、点支付前，用同一方法再读一次（A 设计 MO-04）。金额变了或超上限就放弃，与托管页相同。
- **档位**：档位按钮引擎不碰，档位对错靠金额核对把关（§5.10）：金额低于最低金额（选错了便宜档、被套了优惠）或超过上限，都在注资前放弃。

### 5.7 内嵌页：填表

**必填**：卡号、有效期、CVC，选择器沿用 `Sel.CardNumber`、`Sel.Expiry`、`Sel.CVC`。任一填不上就报错，不点支付。

**入口校验**：`Fill` 碰页面之前先校验卡片（`Card.validate`）和账单地址（`Billing.validate`）。账单地址任何字段（姓名、街道、城市、州/省、邮编、国家、邮箱）含控制字符就报「账单地址含控制字符（字段名）」，不带值，什么都不键入：逐字键入会把 `\n`、`\r` 当回车发出去。托管页同样适用。持卡人姓名来自卡池，`payengine` 在取到姓名之后、注资之前就做同样的检查，含控制字符报 `card_info_failed`「该卡持卡人姓名含控制字符，无法填写账单信息」，不带姓名，不注资。

**地址字段按页面决定**：国家、州、城市、邮编、姓名、街道。DOM 里有的都要填上，DOM 里没有的才跳过。

- 卡号填完后，第一个要找的字段最多等 `addressWait`，之后每个只看当下有没有。例外：下拉框（国家）的值真的改了（`chooseOption` 返回 changed），地址表单会重绘，重绘可能比固定的 `reflowDelay`（500ms）慢，所以下一个字段仍最多等 `addressWait`，不马上记成「页面没有」。`TaxFreeAddress` 总给 US，PH 单每笔都会把国家从 PH 改成 US；记成「页面没有」的字段之后又出现，末尾补查就会放弃，而这时卡已经注资（终审 M4）。
- 顺序：国家 → 试一次点手动地址入口（`revealAddress`）→ 姓名 → 需要时选地址联想展开（见下）→ 街道 → 城市 → 州/省 → 邮编 → 末尾补查。国家先选，因为改国家会重绘其余字段。
- 每个有值的字段分三种情况：
  - 可见：照常填写并核对。
  - 不可见、但 DOM 里有（`findAny` 判断）：当作折叠起来的必填字段，先展开再填；展不开就报错，Fill 失败，不点支付。
  - DOM 里没有：跳过，填表报告里记「页面没有」。
- 展开折叠字段有两条路：
  - 页面有手动地址入口：同托管页，点入口（次数受 `revealMaxClicks`、`revealGap` 限制），展不开报「找不到「X」输入框」。
  - 页面没有手动地址入口、也没点过：城市、州/省、邮编里有值的字段中，至少一个在 DOM 里但不可见时，执行 `expandBySuggestion`：
    1. 街道值含控制字符就不键入（入口校验已经挡过，这里再挡一次），报「账单街道含控制字符」。
    2. 找到可见的街道输入框，选中（`focusField`，见下）、清空，逐字键入账单街道（`typeKeys`，`slowKeyDelay`）。不按 Esc（会关掉联想），绝不按回车（Stripe 输入框里回车可能触发提交）。
    3. 找可见的 `[role="option"]`：跳过主页面，按 frame 顺序每个 frame 取第一个可见选项，用 `clickOption` 点；点不成就试下一个 frame，本轮都不成就下一轮再试。
       - 先等 `suggestRetypeWait`（3 秒）。一个可见选项都没看到，就重打一次街道：重新找街道框（之前的句柄可能已被释放）、选中、清空、再逐字键入一遍，然后在 `suggestWait`（8 秒）内照上面找、点。只重打 1 次。依据 2026-11-04 实测：第一次键入「7114 Cedar Ln」0 个选项；设焦点、清空、重打后 5 秒内地址 iframe 和下拉 iframe 里共出现 5 个选项。推断联想库在第一次键入时才开始加载。
       - 看到过选项、只是没点成，就不重打，接着等满 `suggestWait`。
       - 一直没点成报「地址联想没有出现，无法展开城市、州、邮编」，括号里附「已重打 1 次街道」（重打过时）和最后一次没点成的原因（看到过选项时，如「点击落点是别的 iframe，没有点击」），只有标签名和固定文字。填表报告记「手动地址：地址联想没有出现；已重打 1 次街道」。
    4. 点中后看折叠的字段是否全部展开：每个都可见，而且过落点检查（`landsInOwnFrame`，见下），之后点它们才不会落到主页面上。`suggestRetryWait`（2 秒）内没展开，换一个没点过的 frame 里的选项再点一次（最多点 `suggestMaxClicks` = 2 次）；从第一次点算起等满 `addressWait` 仍没展开，报「选了地址联想后城市、州、邮编仍未展开」。
    5. 填表报告记「手动地址：已选地址联想：第 N 个 iframe 的选项」（点了两次写「第 1、2 个」，按 frame 顺序数，主页面不算）；点了没展开记「已点地址联想（未展开）：…」。重打过街道时后面接「；已重打 1 次街道」。
    6. 联想会改写街道、城市、州、邮编；之后照常填街道、城市、州/省、邮编，用账单地址自己的值覆盖。
- 落点检查 `landsInOwnFrame`（只在内嵌页的路径上用）：
  - 把元素滚进视野（`ScrollIntoViewIfNeeded`），读一次中心点。中心点在主页面可视区外、或离边缘不足 `landEdge`（10px）时，滚动「装着这个元素的顶层 iframe」外面的滚动容器，把它滚到可视区中部：
    - 顶层 iframe：沿 frame 的父链往上，找到父 frame 是主页面的那一层，用 `DOM.getFrameOwner` 取它在主页面里的 iframe 元素（元素本身就在主页面时用它自己）。
    - 滚动容器：从这个 iframe 元素往上，按纵、横两个方向分别看：那个方向的 overflow 是 auto、scroll、hidden 或 clip，而且内容比框长，就算这个方向可滚。至少一个方向可滚的祖先由近到远逐个 `scrollBy({left, top, behavior: 'instant'})`，只沿它可滚的方向滚（只因纵向可滚被选中的容器不横着滚）；近的滚到头还差的交给更外一层，最后是 `document.scrollingElement`（两个方向都滚）。差值是元素中心与可视区中心之差。hidden 用户滚不动、脚本能滚，浏览器自己的滚入也会滚它；clip 脚本也滚不动，`scrollBy` 位移是 0，差的照样交给外层。
    - 只是脚本滚动，不发任何鼠标、键盘事件。
    - 滚完仍在可视区外，下面 `elementFromPoint` 读不到元素，照旧不通过、不点击。
    - 依据 2026-11-04 实测：视口 1366×757，主页面 `document.scrollingElement` 是 html，滚不动；真正的滚动容器是 `MAIN`（overflow-y: auto，scrollHeight 1456）。地址 iframe 在 MAIN 首屏以下，对街道框 `ScrollIntoViewIfNeeded` 后 quad 不变、MAIN 的 scrollTop 仍是 0，落点检查报「点击落点不在页面上」。上一版只滚 `window`，对这种页面没用。
  - 等位置停稳：
    - 没滚动过：隔 `landSettle`（50ms）读两次中心点，相差超过 `landTolerance`（1px）说明还在移动，不通过。
    - 滚动过（`ScrollIntoViewIfNeeded` 让中心点变了，或脚本滚动真滚了）：先等 `landScrollSettle`（150ms），再每隔 50ms 读一次，相邻两次相差不超过 1px 就算停稳，用这次的位置；从开始等算起到 `landScrollMax`（1 秒）还在变，不通过。理由：滚动会触发页面的滚动监听（收起吸顶栏、懒加载改布局），要多久不一定；固定等 150ms 太短时，会把还在调整的布局判成「位置还在变」，点支付就在注资之后放弃；固定等得长又拖慢每个字段。仿造页 `scrollshift=1`（滚动后约 300ms 逐帧改布局）锁住这一条。
    - 两次读位置只看得出主线程上的移动；点支付前的最后检查另看正在跑的动画（§5.8）。
  - 在主页面上用 `document.elementFromPoint` 看中心那一点，必须是承载这个元素的 iframe（元素所在 frame 或它的上层）。主页面上的元素一律不通过。
  - 原因：地址 iframe 带 `scrolling="no"`，内文档比 iframe 高，元素可能在 iframe 可视区之外；`getContentQuads` 不按 iframe 裁剪，坐标可能落在主页面别的元素上，而支付按钮就在主页面。
- 用到落点检查的点击：
  - `clickOption`（点联想选项）：先确认选项本身不是提交控件（`submitControlJS`），再过落点检查，检查紧挨着鼠标点击；任一不过就不点。
  - `focusField`（选中要填的输入框：卡号、有效期、CVC、姓名、街道、城市、input 形式的州、邮编，键入联想前的街道框，以及 3DS 验证码框）：内嵌页上先确认它不是提交控件（是就不点、也不设焦点，报错：焦点落在提交控件上，之后键入的回车、空格会直接触发它），再过了落点检查才用鼠标点；不过就不发任何鼠标事件，改用 `DOM.focus` 直接设焦点。托管页的 `focus`/`click` 不变。
    - 直接设了焦点的字段记进填表报告一行「直接设焦点：街道地址（点击落点不在页面上）、…」：括号里是落点检查的错误文字（去掉「，没有点击」）；鼠标点了焦点却没过去时写「鼠标点了，焦点没过去」。不带任何值，同一字段只记第一次。
  - `clickBox`（点勾选框：`setCheck` 里的 Link 保存、同意条款，`EnsureNoSavePayment` 第一轮的保存付款信息）：内嵌页上同 `clickOption`，不是提交控件、过了落点检查才用鼠标点；落点不对就不点，由原有的脚本点击（`this.click()`）接手，再读勾选状态核对，核对不对照旧报错。真的改用了脚本点击时，填表报告在结果后面接「；改用脚本点击（原因）」，如「Link 保存：已取消；改用脚本点击（点击落点是主页面上的 button，不是 iframe）」；`EnsureNoSavePayment` 的返回值不变，只有报告多这一段。
  - 勾选框的每一次点击（`setCheck`、`EnsureNoSavePayment` 里的鼠标点和脚本 `this.click()`，托管页、内嵌页都一样）之前都先查提交控件（`submitControlJS`），是就不点、报错放弃，绝不改用脚本点。原因（终审 I2）：「保存付款信息」按 `[role="checkbox"]` 和文字认，而结账 form 里不写 type 的 `<button role="checkbox">` 默认就是提交按钮，点它（鼠标或脚本）就是一次没有先置位的付款，之后会被当成「未提交」。错误如「无法确认「保存付款信息」没有勾选: 目标是提交控件，拒绝点击」「勾选「同意条款」失败: 目标是提交控件，拒绝点击」。
  - `clickEntry`（点按文字找到的入口：`tryReveal` 的手动地址入口，`revealCardForm` 的「新卡」「Pay without Link」）：内嵌页上同 `clickOption`，不是提交控件、过了落点检查才点；不过就不点，算没点成，照原逻辑接着等或报错。主页面上的入口因此在内嵌页上一律不点。原因写进报告或错误：
    - 手动地址入口一次都没点成：「手动地址：没点（原因）」；
    - 「Pay without Link」找到了但没点：「Link 验证：要求验证身份，「Pay without Link」没点（原因）」，错误「Stripe Link 要求验证身份，「Pay without Link」点不了（原因），已放弃」。真找不到时才说「页面上没有「Pay without Link」」；
    - 「新卡」入口找到了但没点：错误「找不到「卡号」输入框（「新卡」入口没点：原因）」。
  - 提交控件检查拒绝时的错误文字是「目标是提交控件，拒绝点击」（入口、联想选项、勾选框、输入框共用）。
  - 托管页上，入口仍用 `clickReveal`，勾选框仍用原来的 `click`；唯一的收紧是上面勾选框点击前的提交控件检查。
- 末尾补查：对填表报告里「页面没有」的每一项再用 `findAny` 查一次，这时出现了就报「地址字段「X」填表时没找到、之后又出现了，已放弃」，不静默漏填。
- 填完关联想下拉（`closeSuggestions`，末尾补查之后）：
  - 判定「开着」：任一非主页面 frame 里有可见的 `[role="option"]`，或者街道输入框 `aria-expanded="true"`。没开着什么都不做，报告也不加字。
  - 开着时对街道输入框用 `DOM.focus` 设焦点（不用鼠标点：下拉就在街道下方），按一次 Esc（只发 Esc，绝不发回车），最多等 `suggestCloseWait`（2 秒）轮询到「关着」。
  - 关上了：再按现有核对规则（`fieldHolds`）核对一次街道仍是账单街道，不一致就报「关联想下拉后街道地址被改了，已放弃」；关上后找不到街道框也报错放弃（「关联想下拉后找不到「街道地址」输入框，已放弃」）。
  - 2 秒内关不上（含找不到街道框、设不了焦点）：不报错，继续；点支付前的落点检查（§5.8）会兜住点击。
  - 填表报告沿用「手动地址」那一行，后面接「；联想下拉已关闭」或「；联想下拉没关上」。
  - 依据 2026-11-04 07:23、07:34 两次实页试运行：Fill 返回 20 秒后联想下拉还开着——主页面上一个单独的下拉 iframe（js.stripe.com，`elements-inner-autocomplet…`，`z-index:1`）盖在地址 iframe 的城市、州、邮编那一片上，地址 iframe 里街道 combobox `aria-expanded="true"`。推测是覆盖街道时的键入触发了联想请求，Esc 先于异步结果到达，结果回来后下拉又打开了。
- 依据 2026-11-04 真实页面实测（pro_5x US，测试卡，未点支付）：
  - 账单地址在 js.stripe.com 的一个 iframe 里（Stripe Address Element）。主页面上这个 iframe 高 249px，iframe 内文档高 506px。
  - 填完卡号后，国家、姓名、街道可见；城市、州、邮编在 DOM 里，但所在格子 `opacity:0` 且在 iframe 可视区下方。
  - 页面上没有「Enter address manually」或任何「手动」文字；按 Tab、点别的输入框都不展开。
  - 在街道（`role=combobox`）里逐字键入，4 秒内出现 Google 地址联想：一份在单独的下拉 iframe 里，地址 iframe 内也有一份 `role=option`。
  - 早先整段输入后按 Esc，联想被关掉，从来不会展开，每一单都在填表时失败。
  - 点一条联想后城市、州、邮编会展开并自动填上联想的地址，这一点还是推测，下一次实页试运行验证。
- 托管页仍要求必填，不变。

**页面上没有的元素一律跳过，不算错**：条款勾选框、Link 保存勾选框（`#enableStripePass`）、邮箱框、手机框、「使用新卡」入口。手动地址入口只在地址字段折叠时才点，没有也不算错（没有入口时改走地址联想）。

- 这些在内嵌页上都没有。
- 现有的 `revealCardForm` 对 Link 验证框（「Pay without Link」）的处理保留，因为 Payment Element 也可能弹出 Link 验证。

**保存卡**：内嵌页填表后调用 `EnsureNoSavePayment`，确认「Save payment details … for future purchases」没勾，勾着就取消。

- 这是点数单现成的逻辑，按标签文字识别，`#payment-savePaymentInput` 能命中。
- 确认不了就报错，不点支付。
- 现在 `fillOnly` 只对点数单调用它，改为点数单和内嵌页都调用；托管页的开通单不变。

**不碰**：档位按钮、Apple Pay、PayPal 标签、返回按钮。

**填完先失焦**（只在内嵌页，`blurFrames`，在最后核对之前）：对各 iframe 里有焦点的元素调 `blur()`（iframe 元素本身不碰），失焦了就等 `blurSettle`（500ms）。只失焦，不点击、不发按键。

- 原因：combobox 失焦时自动选中高亮项、改写格式（比如邮编）、页面重算金额这类副作用，于是都发生在最后核对和引擎复核金额之前，能被它们抓住。不先失焦，这些副作用要等点支付、焦点离开 iframe 时才发生，那时已经点下去了。

**最后核对**：全部字段重新核对一遍（`recheckFields`），与托管页相同。

**记下这一份页面**（只在内嵌页，`markFill`，最后核对之后）：记下主页面当前文档的 `loaderId`、装着可见卡号框的 iframe 的 frameId 和它当前文档的 `loaderId`（`Page.getFrameTree`），点支付前核对（§5.8）。找不到卡号框就报错，Fill 失败。每次 Fill 开始先清掉旧的记录。

### 5.8 内嵌页：点击与等结果

**点击**：`Submit` 点 §5.5 确认过的那个主页面提交按钮。

- 「可用」指不是 disabled、不是 `aria-disabled`，也不是 `aria-busy="true"`（`payReadyJS`）。
- 顺序（只改内嵌页，托管页的 `Submit` 不变）：
  1. 最多等 `fieldWait`，等到仍在结账页、主页面唯一可见、可用的提交按钮。「在结账页」指主页面 `location.hostname` 是 `chatgpt.com`、路径以 `/checkout/` 开头（`onCheckoutJS`；数按钮的 `uniquePayButtonJS`、`WaitOutcome` 的 `leftCheckout` 都用它）。
  2. **先失焦再点**（`readyAfterFocus`）：对按钮 `DOM.focus`，把焦点从 Stripe 的 iframe 移到主页面（只设焦点，不点击、不发按键）；固定等 `payFocusSettle`（400ms），让页面对 iframe 失焦的异步反应（校验、重算）跑完；再最多等 `fieldWait`，等按钮重新唯一可用。等不到就报「支付按钮不可点击（可能有字段未通过页面校验），没有点击」等，不置位。焦点此后就在支付按钮上：从这里到点击，绝不能再发任何按键（回车、空格会直接触发它，绕过最后检查和先置位再点的顺序），只许读页面、滚动和最后那一下鼠标点击。
  3. 收集点击前已有的提示（`scanBeforeClick`），再核对一次按钮仍唯一、可用、在结账页。
  4. **点击前最后检查**（`payClickPoint`）：
     - 滚进视野、等停稳（`landPoint`，同 §5.7 的落点检查：`ScrollIntoViewIfNeeded` 能带动 MAIN 滚动；仍在可视区边缘时用脚本滚它外面的滚动容器；没滚动过隔 `landSettle` 读两次，滚动过等停稳），得到中心点 (x, y)。
     - 核对填表之后页面没换过（`checkFillMark`，终审 M3）：主页面文档的 `loaderId` 还是 Fill 时那个，卡号框还在 Fill 时那个 iframe 里、iframe 的文档也没换。整页重新加载、Payment Element 重新挂载（换了新 iframe）或卡片 iframe 自己重新加载，表单就是空的：这时点支付会被 Stripe 前端拦下、不扣款，但 `submitted` 已经置位，这一单要白占一张卡走完确认才释放，还计入熔断。
     - 然后在**同一次脚本**（`payClickJS`）里依次查：仍在结账页（主机名、路径）；主页面可见的 `button[type="submit"]` 正好一个；按钮可用（同上）；主页面的 `activeElement` 不是 IFRAME；按钮没在动——此刻的中心点和 (x, y) 相差不超过 `landTolerance`，按钮和它的上级上也没有正在跑的、改位置或大小的动画（`document.getAnimations()`，只改透明度、颜色、阴影等样子的不算，伪元素上的不算，时间线不是 `DocumentTimeline` 的不算，关键帧里的 CSS 自定义属性 `--x` 不算）；`document.elementFromPoint(x, y)` 命中按钮自己或它的后代。结账页、按钮个数放进这一次求值（终审 M1），滚动、等稳那一会儿页面变了也能拦住。检查和点击之间不再有等待。
     - 为什么另看动画（A3 根因，2026-11-04 本机复现）：transform 动画由合成线程驱动，CDP 隔 50ms 读两次位置时主线程的动画时钟常常只走了 0 或 1 帧，读到同一个值（30 次里 15 次），按钮在屏幕上以 200px/s 移动，两次读位置却判成停稳。
     - 动画判断里不算的两类（终审二 Minor-3）：
       - 滚动驱动的动画（`animation-timeline: scroll()/view()`，时间线是 ScrollTimeline/ViewTimeline）：只随滚动走，落点检查停稳之后、点击之前没人滚动，它就不动；它的 playState 却一直是 running，算上的话支付按钮的上级挂一个这样的动画，每一单都会在注资后被拒点。没有时间线的动画也不走，一并不算。页面自己还在滚动时，两次读位置、中心点核对看得出来。
       - 只改 CSS 自定义属性（`--x`）的：自定义属性自己不改位置和大小。经 `var()` 带动 transform 的，这种动画在主线程上跑，两次读位置、中心点核对看得出来（仿造页用例锁住）。
  5. 全部通过才置位 `submitted`，然后用第 4 步检查过的那个坐标点（不再重新滚动、重新求中心）。
- 任何一步不过：返回错误、不置位，`LockSubmit` 仍返回 false。错误措辞：
  - 落点是别的元素：「支付按钮被挡住（落点是 <标签名或 iframe>），没有点击」；
  - 其余没过最后检查的：「支付按钮没过落点检查（原因），没有点击」，原因如「位置还在变」「点击落点不在页面上」「焦点还在 iframe 里」；位置还在变分三种写（终审二 Minor-3）：落点检查两次读到的位置不同写「位置还在变」，最后检查时中心点偏了写「位置还在变，中心点偏了」，检测到改位置的动画写「位置还在变，检测到动画：<属性>@<标签名>」（如 `transform@button`；属性是 CSS 的连字符写法，标签名是挂动画的元素，不写值、class、文本）。试运行的按钮状态用同样的原因：「可点击，但没过落点检查（原因）」；
  - 按钮不可用：「支付按钮不可点击（可能有字段未通过页面校验），没有点击」；
  - 最后检查时页面变了：「页面已离开结账页，没有点击」「支付按钮不唯一（找到 N 个），没有点击」「页面在填表之后重新加载过，没有点击」「卡号输入框在填表之后换过（卡片 iframe 重新挂载或重新加载），没有点击」。
- 原因：
  - 置位之后只要点了就绝不再点第二次。按钮被盖住时（2026-11-04 实测的联想下拉换一种布局、横幅、弹层），鼠标会点到别处，注资后付款没完成，只能走确认、回收。
  - 不先把焦点移出 iframe，按下鼠标那一刻 iframe 才失焦；页面要是在 iframe 失焦时把按钮短暂设成不可用，按钮在松开之前就不可用了，点击丢失，而 `submitted` 已经置位。仿造页（`busy=blur`）复现过；实页会不会在失焦时重算还没核实，试运行的「等了 X 秒」用来回答这个问题。
- 只点一次的全部机制（先置位、`LockSubmit`、`ErrAlreadySubmitted`）不变。

**试运行的按钮状态**：「试运行到填表」用 `PayButtonState` 把按钮状态写进时间线，只检查、绝不点击。

- 内嵌页和 `Submit` 走同一条路，只是不置位、不点：等按钮唯一可用（最多 `fieldWait`），把焦点移到主页面、固定等 `payFocusSettle`、再等按钮可用（最多 `fieldWait`），最后做上面第 4 步的检查。它在 Fill 末尾的失焦之后执行，看到的是失焦后的真实状态。
- 全部通过报「可点击（填表后等了 X 秒，移焦点后等了 Y 秒）」，X、Y 分别是两段等按钮可用的时间（不含固定的 `payFocusSettle`），保留一位小数：X 看 Fill 返回后页面重算要多久，Y 看实页会不会在 iframe 失焦时重算。
- 最后检查不过：按钮不可用报「存在但不可点击（最后检查时忙）」（前两段都等到了可用，滚动、等稳那一会儿又忙了）；页面变了报「页面已离开结账页」「不唯一（N 个）」「未找到」「页面在填表之后重新加载过」「卡号输入框在填表之后换过（卡片 iframe 重新挂载或重新加载）」；落点是别的元素报「可点击，但落点被挡住（落点是 …）」；其余报「可点击，但没过落点检查（原因）」。
- 等不到报「存在但不可点击（等了 N 秒）」，N 是 `fieldWait`；「不唯一（N 个）」「读取失败」「未找到」措辞不变；看到已离开结账页时报「页面已离开结账页」。
- 依据 2026-11-04 07:23 实测：地址改了，页面重算，Fill 刚返回时按钮 `disabled`、`aria-busy="true"`，1 秒后才可用。只读一次会误报「存在但不可点击」；真实付款的 `Submit` 本来就最多等 `fieldWait`，能等到。
- 托管页仍只读一次，不变。

**等结果**：`WaitOutcome` 按现有顺序判断：成功元素 → 未处理的 3DS 框 → 点击后才出现的提示文字。新增一条：

- 每轮检查主页面地址。主机名不是 `chatgpt.com`、或路径不再以 `/checkout/` 开头时，立即返回 `OutcomeUnknown`，说明文字为「页面已离开结账页」。
- 引擎照旧转确认阶段，由查账号定论。
- 不新增结果类型。确认阶段对 `unknown` 的处理不变。

**3DS**：Stripe.js 在当前页面上弹出验证框，沿用现有的 `Sel.ChallengeFrame`、`EnterOTP` 和 MarsWallex 验证码推送。内嵌页上 `EnterOTP` 另有三条（终审 I1；托管页不变）：

- 验证框不一定是全屏遮罩，验证码框、提交按钮可能在验证框可视区外，按坐标点会点到主页面——可能就是第二次点支付。
- 选中验证码框用 `focusField`（过落点检查才用鼠标点，不过就 `DOM.focus`）。
- 点验证码提交按钮：按钮不能在主页面上、必须在验证框的 frame 子树里；过 `landsInOwnFrame`（主页面上那一点是装着它的 iframe），再用 `DOM.getNodeForLocation` 看那一点最深处落在哪个 frame，也必须在验证框的子树里，才用鼠标点。这里不做「不是提交控件」检查：验证框里的提交按钮本来就该点，它不在主页面上，点它不会是点支付。不过就不点、报错（「提交验证码失败: …，没有点击」），也不改按回车。
- **回车只允许发在 3DS 验证框里**：没有提交按钮时，验证码框在验证框的子树里、`ensureFocus` 确认焦点就在它上面，才按回车。这是「内嵌页绝不发回车」的唯一例外。

不分托管页、内嵌页，`EnterOTP` 开头先查验证码格式（终审二 Minor-1）：先删掉普通空格（U+0020）和横线，再要求结果匹配 `^[0-9A-Za-z]{4,12}$`，页面里只填删过之后的值（2026-11-04 用户决定）。Tab、回车、换行、全角空格、不换行空格等不删，照旧拒绝。验证码是逐字发键的，夹着的 Tab 会把焦点移出验证码框，之后的空格、回车可能落到别处的按钮上。格式不对就报错「验证码格式不对（删掉空格、横线后只接受 4–12 位数字或字母），没有填写」，一个键都不发，错误里不带验证码。卡池收验证码（`cardpool/otp.go`）不拦：管理员要能在后台看到原样的验证码。

**提示文字**：

- 拒付等文字可能出现在 Stripe iframe 里（英文），也可能出现在主页面上（随账号语言）。
- 认不出的照旧只记下、继续等，超时后转确认，不会重复付款。
- 中文等语言的拒付词没有核实，本轮不加。

### 5.9 错误码

只新增一个错误码 `amount_below_floor`（§5.10），前端 `payui.ts` 要补上它的说明。其余都沿用前端已有说明的错误码：

| 情况 | 错误码 | 动钱了吗 |
|---|---|---|
| 内嵌会话缺 `processor_entity` 或格式不合格 | `checkout_failed` | 没有 |
| 链接不在白名单（含 chatgpt.com 路径不对、带查询串） | `checkout_url_untrusted` | 没有 |
| 打开时停在 Cloudflare 挑战页 | `cf_challenge`（告警） | 没有 |
| 打不开、支付按钮不唯一 | `page_failed` | 没有 |
| 读不出金额 | `amount_unreadable` | 没有 |
| 币种不符 | `currency_mismatch` | 没有 |
| 超上限 | `amount_over_cap` | 没有 |
| 低于最低金额 | `amount_below_floor` | 没有 |

### 5.10 金额下限

2026-11-03 用户追加的规则：**金额必须在该套餐预期价格附近，偏低也要在注资前放弃。** 同日用户又定：下限单独填一个数（「最低金额」），不按预期金额的固定百分比算。原因是挂代理后各地区币种不同，有的地区价格可能随汇率浮动，固定比例不好用。

- **防的是什么**：
  - 内嵌页上有档位按钮，页面默认选错了更便宜的档；
  - 页面自动套用了优惠（比如首月 $0）。
  - 只拦上限时，这两种情况都会被照常付款，客户拿到的套餐不对，钱却花出去了。
- **新配置项「最低金额」**：`RegionConf` 加 `FloorMinor int64`（JSON `floor_minor`）。
  - 和预期金额、上限一样，按「套餐 × 地区」各填一份，用该地区币种的最小单位，不做汇率换算。
  - 保存配置时校验：不能为负；填了上限时不能高于上限；填了预期金额时不能高于预期金额。
  - 预期金额 `expect_minor` 仍只用于展示和校验配置，不参与付款判断。
- **真实付款单的规则**：
  - `ResolvePlan` 在非试运行时要求 `FloorMinor > 0`，否则以「套餐 X 在地区 Y 未配置最低金额」判为不可用。这与未配上限、未配注资金额的处理相同。下单和建会话时都会拦下。
  - 打开页面读到金额后，若 `金额 < FloorMinor`，以 `amount_below_floor` 放弃。说明写明页面金额和最低金额，并提示「可能选错了档位或带了优惠」。此时还没注资。
  - 上限仍是 `CapMinor`，不改。税只会让金额变高，由上限把关。
  - 填表后复读金额要求和第一次完全相同（MO-04），下限自然也覆盖到。
- **试运行**：金额偏低只在时间线记一条 warn，不放弃。没配最低金额时，记一条「未配置最低金额，跳过下限检查」。
- **适用范围**：托管页、内嵌页、开通单、点数单都适用，按单据的套餐和地区取配置。
- **最低金额从哪里来**：建会话这一步已经调用了 `ResolvePlan`，把它返回的 `FloorMinor` 记在运行期的 job 上。不落库，也不改单据表。
- **出厂值：美国、菲律宾内置价格区间（2026-11-04 用户要求，价格是固定的，不需要人填）**。预期金额、最低金额、上限由程序内置，管理员可改；日本、智利、埃及仍要手填。金额都是最小单位，整数运算：预期、最低向下取整，上限一律向上取整（代码里是 `capOf`，US、PH 订阅、PH 点数都一样）。
  - 区间规则：
    - US：预期 = 最低 = 标价，上限 = 标价 × 110%（向上取整）；
    - PH 订阅：预期 = 最新标价 L，最低 = L_low × 7/8（等于 ÷1.12 再 ×0.98），上限 = L_high × 102%（向上取整），L_low、L_high 是已知标价里的低值和高值；
    - PH 点数：预期 = ₱565 × 数量 / 250，最低 = 预期 × 7/8，上限 = 预期 × 112%（向上取整）。
  - 价格表（预期 / 最低 / 上限）：

    | 套餐 | US（美分） | PH（比索分） |
    |---|---|---|
    | go | 800 / 800 / 880 | 30000 / 26250 / 30600 |
    | plus | 2000 / 2000 / 2200 | 99900 / 87412 / 112200 |
    | pro_5x | 10000 / 10000 / 11000 | 649000 / 567875 / 661980 |
    | pro_20x | 20000 / 20000 / 22000 | 999000 / 874125 / 1018980 |
    | pro_50x | 50000 / 50000 / 55000 | 3249000 / 2842875 / 3313980 |
    | credit250 | 1000 / 1000 / 1100 | 56500 / 49437 / 63280 |
    | credit25000 | 100000 / 100000 / 110000 | 5650000 / 4943750 / 6328000 |

    其余点数档按同一规则线性计算。
  - 来源（2026-11-04 查得）：
    - US 是网页价，不含销售税：Go $8、Plus $20、Pro 5x $100、Pro 20x $200、Pro 50x $500（OpenAI 帮助中心「About ChatGPT Pro tiers」写了三档 Pro 价格，第三方 2026-10/11 汇总一致；pro_5x 的 100.00 USD 已在真实结账页实测）；Codex 点数每 250 点 $10，线性（调研文档 §1，2025 年数据）。
    - PH 是含 12% 增值税的标价：Go ₱300、Plus ₱999、Pro 5x ₱6,490、Pro 20x ₱9,990（GeoSub 采集的 App Store 价，2026-11-02）；Plus 在 2025-10 上线时的网页价是 ₱1,100，所以 Plus 的上限按 ₱1,100 算；Pro 50x ₱32,490（含税），免税价 ₱29,008.93（ZovoCard 文档里的实测网页价）；Codex 点数每 250 点 ₱565（取自 ZovoCard）。
    - PH 实际扣款是含税价还是免税价，取决于账单地址，目前没核实，所以区间同时覆盖两种。PH 价格来自 App Store 与 ZovoCard 的网页数据，不是真实结账页的实测：第一次 PH「试运行（只读金额）」会核对；超出区间的单子在注资前放弃（`amount_below_floor` 或超上限）。
  - 补齐规则：加载已存配置时，US、PH 地区的币种为空或等于内置币种，则预期、最低、上限里为 0 的用内置值补上；非 0 的值（管理员改过的）不动；币种不同不补。另有几条边界，保证补完仍能通过保存校验、而且不会把下限放低：
    - 上限：内置上限放不下管理员的非 0 预期或非 0 最低时，上限不补；
    - 预期：补上后会大于管理员的非 0 上限，或者内置预期小于管理员的非 0 最低时，预期不补；
    - 最低：管理员的预期、上限都为 0 或不低于内置最低时，补内置最低；管理员填了非 0 预期或非 0 上限、而且低于内置最低时，最低不补、留 0，真实付款单由 `ResolvePlan` 以「未配置最低金额」拒绝（下单、建会话时拦下，不注资；试运行不受影响）。不按预期或上限把最低降下来：比如 pro_5x 的预期或上限错填成 Plus 的 $20，最低降到 $20，页面默认选错成 $20 的 Plus 档时就会过下限，付了钱、套餐却不对。（终审二 Minor-2 之前，上限低于内置最低时最低会降到上限，现已改为留 0。）
    - 启用开关和注资金额不补。补出来的值保存前只在内存里。
  - 查不到内置价（`BuiltinRegionPrice` 返回 false）时什么都不补。
  - **订阅与点数的区间会重合**：比如 US 的 plus（$20）与 credit500（500 点 $20），PH 的 plus 与 credit500 也有重叠。金额下限、上限分不出页面上卖的是订阅还是点数，混淆靠建会话这一层防：开通单只用 `CreateCheckout` 按单据自己的套餐名建订阅会话，点数单只用 `CreateCreditCheckout` 按数量建点数会话，付款页上的商品由会话决定，引擎不会拿一种单子的会话去付另一种。
  - 接口 `GET /api/v1/admin/pay/config` 多返回 `builtin`（套餐键 → 地区 → 币种、预期、最低、上限），后台「恢复内置价格」直接用它，前端不再保留镜像常量。
- **怎么填**：
  - 价格固定的地区，最低金额填标价；
  - 价格随汇率浮动的地区，最低金额填低位价，上限填高位价；
  - 注资金额是美元。付非美元金额时，发卡方按汇率扣美元，可能另收手续费，所以注资金额要按高位汇率留出余量。
- **升级注意**：已有安装里保存过的套餐配置都没有最低金额。升级后，美国、菲律宾空着的金额自动用内置价补上，不用填；日本、智利、埃及在填好最低金额之前不可下单，管理员要在后台补上。写进 CHANGELOG 的「升级注意」。

## 8. 实测结论与未核实事项

### 8.1 已实测（2026-11-04，本机 18090，免费号 Pro 5x US，公开测试卡，未点支付）

§7 第 1 步已完成：「试运行（只读金额）」和「试运行到填表」都跑通，最后一次在 657f604 上，9 个字段全部核对一致，金额复核一致，支付按钮「可点击（等了 0.5 秒）」。下面是这几轮实测得到的页面事实，§5 的规则都以它们为依据。

- **页面与金额**：
  - 页面顶部有 US$100 / US$200 / US$500 三档用量选择，pro_5x 默认选中 US$100；
  - 免税地址下「预估税额 US$0.00」，填完地址后复读金额不变（100.00 USD）。
- **卡片**：Stripe Payment Element 在 js.stripe.com 的 iframe 里，只有卡号、有效期、CVC。
- **账单地址**：
  - 填完卡号后出现 Stripe Address Element（另一个 iframe）。国家、姓名、街道可见；城市、州、邮编在 DOM 里但折叠（`opacity:0`，在 iframe 可视区下方）。
  - 页面上没有「Enter address manually」，按 Tab 或失焦都不会展开。
  - 唯一的展开方式是在街道里逐字键入，再点一条 Google 地址联想。
  - 第一次键入常常不出联想（联想库懒加载），清空重打一次就有。
  - 点中联想后，城市、州、邮编展开并填上联想的地址，再用我们自己的值覆盖。
- **联想下拉**：
  - 下拉是主页面上一个单独的 iframe（`z-index:1`），地址 iframe 里也有一份 `role=option`。
  - 覆盖街道时的键入会再次触发联想，异步结果回来后下拉会重新打开，盖住城市、州、邮编那一片。落点检查会拒绝点到它。
  - 对街道 `DOM.focus` 后按 Esc 能关掉（§5.7）。
- **滚动**：
  - 视口 1366×757。主页面 HTML 不滚动，真正的滚动容器是 `main`（`overflow-y:auto`），地址 iframe 在首屏以下（top≈1106）。
  - CDP 的 `ScrollIntoViewIfNeeded` 对跨源 iframe 里的元素不会带动父页面的 `main`，`window.scrollBy` 也无效。
  - 改为在主页面用脚本滚动 iframe 外层的滚动容器后，落点检查正常（§5.7）。
- **支付按钮**：
  - 主页面唯一的 `button[type="submit"]`，文字「升级至 Pro」。
  - 地址改动后会进入约 1 秒的 `disabled` + `aria-busy="true"` 状态（页面重算）。
  - 把焦点移出 iframe 后，固定等 400ms 就可用，没有再看到长时间重算。
  - 按钮中心点 `elementFromPoint` 命中按钮本身。
- **Link**：这个账号没有出现 Link 保存勾选框，也没有弹出 Link 验证框。
- **开页限速**：
  - 短时间内连续建结账会话（第 8、第 10 个），开页会卡在「正在准备您的套餐」约 60 秒；
  - 每次间隔 10 分钟以上就正常。
  - 引擎每单只建一次会话，正常使用碰不到。但排查时不要连续开页。
- **Cloudflare**：本机住宅 IP 开页没有遇到挑战。

### 8.2 仍未核实

下列问题要靠 §7 后面几步回答。认不出的情况都会走确认阶段，不会重复付款。

- 点支付后页面跳到哪里，有没有可识别的成功元素。
- 拒付、3DS 在内嵌页上的实际样子。
- 账号邮箱注册过 Stripe Link 时，Payment Element 的验证框长什么样。
- PHP 等其他币种下金额的写法；PH 地址表单是否同样折叠、靠联想展开。
- PH 等非美元地区的页面价是 OpenAI 定的固定本地价，还是按汇率换算、每天浮动；含不含税（§5.10 的内置区间按两种都覆盖，第一次 PH「试运行（只读金额）」核对）。
- 有应税地址时税额会不会让金额变化（引擎只用免税地址）。
- VPS 机房 IP 和各地区代理会不会触发 Cloudflare 挑战。
- 其他地区、其他网络条件下，失焦后的重算会不会晚于 400ms 才开始。重算在最后一步检查之前开始时，会判成不可点，没有点击，单子安全失败、卡里的钱回收；晚于检查才开始时，点击仍可能丢失，只能走确认、回收。看到这类单子就加长这个等待。

## 9. 否决的方案

- **B：自建付款页**，用返回里的 `client_secret` 加载 Stripe.js 付款，不经过 chatgpt.com。否决原因：
  - 要用 OpenAI 的 Stripe 公钥在别的来源上运行它的结账；
  - 绕开了 OpenAI 页面自己的风控；
  - 容易被判成异常，连累用户账号；
  - 没有任何稳定性保证。
- **C：纯接口**，由服务器直接调 Stripe 和 ChatGPT 接口确认付款。否决原因：
  - 完整卡号要经我们的服务器发给 Stripe；
  - 3DS 仍要浏览器；
  - 同样绕开了页面风控。
