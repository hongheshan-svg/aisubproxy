# 首页售后查询设计

日期：2026-11-04。状态：设计已分段确认，待用户审阅全文。

本文是「代理商全自动」项目的第 1 个子项目，整体拆分见文末「所属项目」。

## 1. 目标

最终用户在首页粘贴一张卡密，不跳页，就能看到：
- 这张码现在怎么样了；
- 失败的话，原因是什么、自己下一步怎么做；
- 成功的话，开通了什么、什么时候到期（到期时间取 ChatGPT 给的真实值，不推算）；
- 这张码被换过新码的话，新码是什么。

做成的标准：常见的售后问题，用户自己查就能解决，不用找售卖方或我们。具体有：码用没用过、为什么失败、能不能重新提交、换出来的新码是什么。

## 2. 范围

**做：**
- 首页加「售后查询」区块，一次查一张。
- 卡密查询接口加字段，`/history` 批量查询也带上这些字段。
- 失败原因归到一套固定的「指引编号」，前端按编号显示自助指引，中英文都要有。
- 修现有漏洞：上游服务商分支返回的是完整邮箱；`/history` 导出的 CSV 也有完整邮箱。

**不做：**
- 自动换码。那是第 5 个子项目，本子项目只把已经存在的换码结果显示出来。
- 代理商归属、代理商联系方式（用户已决定不显示）。
- 平台客服联系方式。
- 新的服务商接入。

## 3. 架构：两层，与服务商无关

卡密属于哪家服务商，由现有的服务商注册表 `provider.ForCode` 决定。服务商有两类：
- **供卡型**（实现 `provider.CardSupply`，现在有 MarsWallex）：我们用自己的卡付款；
- **上游发码型**（实现 `provider.Upstream`，现在有 ZovoCard）：对方负责开通。

以后会接入很多家，所以查询分成两层。

### 3.1 服务商层：只回答「这张码现在什么情况」

每家返回同一个结构 `afterSaleFacts`：

| 字段 | 含义 |
|---|---|
| `Found` | 是否认得这张码 |
| `Status` | `unused` / `processing` / `used` / `failed` / `disabled` / `replaced` / `unsupported`（没有查询能力时由公共层填） |
| `Reusable` | 失败后码是否已恢复、能否重新提交 |
| `Plan` | 套餐键 |
| `PlanKind` | `subscription` / `credit` / 空 |
| `ExpiresAt` | 权益到期时间，服务商确知时才填；不推算 |
| `UsedAt` | 开通成功的时间 |
| `Renewal` | `off`（已关闭并核实）、`closing`（正在关闭）、空（其他情况） |
| `Guide` | 指引编号，取值见第 4 节的固定列表 |
| `ProviderNote` | 服务商原文说明，可以为空 |
| `AccountEmail` | 原样返回。打码由公共层统一做，服务商层不负责 |
| `Replacement` | 这张码换成了哪张新码（完整码）。没换过，或者我们库里没有完整新码，就为空 |
| `ReplacedButUnknown` | 换过码，但库里没有新码的完整码 |

**能力接口**：沿用现有的「可选能力」写法。
- 现有的 `upstreamLookuper`，改成返回 `afterSaleFacts`。
- 供卡型服务商**共用一套实现**，从本站的码表和付款引擎订单推出结果，所以以后接入的供卡型服务商不用另写。具体规则：
  - `ExpiresAt` 取订单上记下的 `access_until`，没有就为空。
    - 记录方式：续费核实那一步本来就会调 `GET /subscriptions`。读 `will_renew` 时，顺带解析同一响应里的 `active_until`，写到 `pay_orders.access_until`（新列，Unix 秒，可为空）。
    - 只多读一个字段，不碰钱。格式认不出就不写。
    - 已有的单，会话已经清空，补不了，所以不显示到期时间。
    - 点数码没有到期时间。
  - `Replacement`：本站码换码时，新码的完整码不入库（库里只有哈希和前缀），所以换过的码一律 `ReplacedButUnknown=true`。第 5 个子项目（自动售后）要显示新码，必须先解决新码完整码的保存问题（加密存储）。
  - `Renewal` 由订单的续费状态映射：`cancelled` → `off`，`pending` → `closing`，其他 → 空。
- 上游发码型服务商**各自实现**查询，把 ZovoCard 现有的查询改成这个形式。
  - `ExpiresAt` 由它自己给，不知道就为空。
  - 自己的错误码能对上指引列表就对上；对不上的，按 `Reusable` 归为 `provider_retry` 或 `provider_wait`，同时把原文放进 `ProviderNote`。
- 服务商没有查询能力：`Status=unsupported`，显示「这张卡密暂不支持在线查询，请联系售卖方」。

### 3.2 公共层：只有一份，所有服务商都经过它

1. **分派**：用 `provider.ForCode` 找到服务商，调它的查询能力。注册表不认得的码，返回 `unknown`。
2. **打码**：`AccountEmail` 一律打码，规则和本站码现在用的 `maskEmailForAdmin` 一样。服务商层给的是完整邮箱也会在这里被打码。
3. **清洗原文**：`ProviderNote` 截断到 200 个字符，并把里面像邮箱、长令牌（20 位以上的连续字母数字）的部分替换成 `***`。
4. **跟换码链**：`Replacement` 不为空时，用新码重新做第 1 步，所以新码属于别的服务商也能接着找。
   - 最多跟 5 层。超过 5 层，或者遇到已经走过的码，就停下，返回最后一张能确认的码。
   - 返回给前端的是最终那张码，以及它自己的状态。
5. **到期时间**：只有 `Status=used` 并且服务商给了 `ExpiresAt` 时才返回，原样输出，不推算。
6. **字段白名单**：返回字段只从下面第 5 节的列表里出。

## 4. 指引编号（固定列表）

后端只返回编号，文字放在前端语言包 `zh.ts` 和 `en.ts`。以后改文字不用动后端。新服务商一般不需要新增编号。

| 编号 | 什么情况用 | 给用户看的指引 | 按钮 |
|---|---|---|---|
| `session_invalid` | 账号登录已失效 | 重新登录 ChatGPT，按教程重新复制 session，再兑换 | 重新兑换 |
| `already_subscribed` | 账号已有订阅 | 这个账号已经有订阅了。<br>在 App（Google Play、App Store）里买的，要先在 App 里取消，等到期。<br>在网页上买的，也要等到期。<br>不想等，就换一个没有订阅的账号来兑换 | 重新兑换 |
| `plan_unavailable` | 套餐暂不可用 | 稍后再试；一直失败就联系售卖方 | 重新兑换 |
| `credit_needs_subscription` | 点数码：账号没有 Plus/Pro，或套餐不符合 | 点数码只能给已开通 Plus 或 Pro 的账号用。先开通会员再兑换 | 重新兑换 |
| `credit_not_personal` | 点数码：不是个人账号 | 只支持个人账号，团队或企业账号用不了，请换个人账号 | 重新兑换 |
| `credit_delinquent` | 点数码：账号欠费 | 先到 ChatGPT 把欠费结清 | 重新兑换 |
| `credit_region_mismatch` | 点数码：计费币种和卡密地区对不上 | 这张码的地区和你账号的计费地区不一样，请联系售卖方换一张对应地区的码 | 无 |
| `retry_later` | 其他失败，确认没有发起付款 | 这次没开通成功，也没有扣款，稍后可以重新提交 | 重新兑换 |
| `manual_review` | 付款被拒、多次失败、结果确认中 | 已转人工核对，请不要重复提交，处理完再来查 | 无 |
| `provider_retry` | 服务商给的原因归不了类，码已恢复 | 原样显示服务商原文，加一句「可以重新提交」 | 重新兑换 |
| `provider_wait` | 服务商给的原因归不了类，码没恢复 | 原样显示服务商原文，加一句「请等待处理，或联系售卖方」 | 无 |

供卡型服务商的错误码，对照现有的 `localFailureText`（`backend/internal/handler/local_cdk.go`）：

| 现有错误码 | 指引编号 |
|---|---|
| `session_invalid` | `session_invalid` |
| `already_subscribed` | `already_subscribed` |
| `plan_unavailable` | `plan_unavailable` |
| `credit_no_subscription`、`credit_plan_ineligible` | `credit_needs_subscription` |
| `credit_not_personal` | `credit_not_personal` |
| `credit_delinquent` | `credit_delinquent` |
| `credit_currency_mismatch` | `credit_region_mismatch` |
| 其他干净失败（码恢复可用） | `retry_later` |
| 派生原因 `declined`、`attempts_exhausted`、`needs_review` | `manual_review` |

## 5. 接口

`GET /api/v1/lookup/cdk` 和 `POST /api/v1/lookup/cdk/batch`：路径不变，限流照旧（`LookupGuard`）。

返回里现有的字段都保留，含义不变，老前端不受影响：`cdk_code`、`status`、`used`、`can_resubmit`、`account_email`（改为一律打码）、`plan`、`used_at`、`notes`、`message`。

`status` 新增两个取值：
- `replaced`：已换发新码；
- `unsupported`：服务商不支持在线查询。

新增字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `plan_kind` | string | `subscription`、`credit` 或空 |
| `expires_at` | string（RFC3339）或省略 | 权益到期时间（ChatGPT 给的真实值） |
| `renewal` | string | `off`、`closing` 或空 |
| `guide` | string | 第 4 节的编号，没有就为空 |
| `provider_note` | string | 清洗后的服务商原文 |
| `replacement` | object 或省略 | `{ code, status, depth }`：最终那张新码的完整码、它的状态、经过了几层 |
| `replaced_unknown` | bool | 换过码，但库里没有新码的完整码 |

## 6. 前端

- **首页**：`HomeView.vue` 的标题下方加「售后查询」区块，包括输入框、查询按钮，结果显示在区块里。另给一个「批量查询」链接到 `/history`。
- **纯函数**：在 `frontend/src/lib/` 新增一个纯函数，把一条查询结果转成显示模型：标题、说明、要显示的字段、按钮。首页和 `/history` 的单条结果都用它。页面组件里只负责调用。
- **各状态显示什么**：

| 状态 | 显示 | 按钮 |
|---|---|---|
| 未使用 | 「这张卡密还没用过」 | 去兑换（带上卡密跳到 `/recharge`） |
| 排队、处理中、人工核对中 | 当前进度，加「请勿重复提交」 | 无 |
| 成功 | 套餐、开通时间、到期时间（有才显示）、打码邮箱。<br>`renewal=off` 时加「已关闭自动续费，到期不会扣款」；`closing` 时加「正在关闭自动续费」。<br>点数码显示「点数已到账」，不显示到期时间 | 无 |
| 失败，码已恢复 | 失败原因，加对应的指引 | 重新兑换 |
| 失败，码没恢复 | 「已转人工核对」或服务商原文，加「请勿重复提交」 | 无 |
| 已换发新码 | 完整显示新码，以及新码的状态 | 复制、去兑换 |
| 换过码但库里没有完整新码 | 「已换发新码，请联系售卖方获取」 | 无 |
| 不支持在线查询 | 「这张卡密暂不支持在线查询，请联系售卖方」 | 无 |
| 已禁用、找不到 | 对应提示 | 无 |

- **导出**：`/history` 导出 CSV 时，`account_email` 用接口返回的打码值。
- **语言包**：新文案全部进 `zh.ts` 和 `en.ts`，两边的键要一致。

## 7. 出错时怎么处理

- 服务商查询报错或超时：返回 `status=unknown`，`message` 写「暂时查不到，请稍后再试」，不带错误细节。服务端记日志，日志里不放邮箱和令牌。
- 换码链中途某一层查询失败：停在上一张已经确认的码，`replacement` 只返回到那一层。
- 批量查询：保持现在的单次上限，每条单独处理，一条出错不影响其他条。

## 8. 测试（先写测试，看它失败，再写代码）

**后端**
- 用一个假的上游发码型服务商和一个假的供卡型服务商注册到注册表，验证分派正确、两层分得开。
- 服务商层返回完整邮箱，接口响应里不能出现完整邮箱。断言响应 JSON 里不含原始邮箱字符串，单条和批量都要测。
- 修漏洞：ZovoCard 分支三个来源的邮箱都要打码，分别是 `recharge_tasks`、绑定记录、卡台 Result。
- 不支持在线查询的服务商返回 `unsupported`。
- 供卡型服务商：每种派生状态和错误码，都对到第 4 节的指引编号（表驱动）。`Renewal` 的映射也要测。
- 换码链：换过 1 次；连换 2 次；跨服务商；绕成一个圈；超过 5 层；新码不在库里；中途某一层查询失败。
- 到期时间：
  - 续费核实时，`active_until` 分别是 RFC3339 字符串、Unix 秒数字、毫秒数字、缺失、乱值，前三种写入，后两种不写，也不报错；
  - 查询时只在 used 且有值时返回；
  - 已有的单（没有值）不返回。
- 服务商原文清洗：超过 200 个字符要截断；里面的邮箱和长令牌要被替换。

**前端**
- 纯函数：每个状态加每个指引编号，对应的显示模型（vitest）。
- 中文和英文语言包的键必须一致。

## 9. 上线

- 数据迁移只有一处：`pay_orders` 加 `access_until` 列（可为空），其余都是加字段和打码。
- 会改变现有行为的只有一处：上游服务商分支返回的邮箱变成打码的。已经在用 `/history` 导出的代理商，导出文件里也会看到打码邮箱。CHANGELOG 要写明这一点。
