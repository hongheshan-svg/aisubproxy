# 订阅套餐「允许 0 元开通」设计

日期：2026-11-11
状态：用户已批准方案（方案 2）

## 1. 背景

- 用户在 ChatGPT 官网看到「Plus 首月免费」活动，链接形如 `https://chatgpt.com/?…&promo_campaign=plus-1-month-free#pricing`，结账时应付 0 元。
- 本站建结账会话（`chatgpt/client.go` 的 `planCheckoutBody`）只带 `plan_name` 和 `billing_details`，不带任何优惠参数，所以正常情况下结账页是原价。
- 但如果 ChatGPT 自己把优惠套到本站这一页上，页面会显示 0 元。这时引擎在 `payengine/worker.go` 的下限检查里，以 `amount_below_floor` 放弃这一单（还没注资）。
- 这条下限检查本来就是防这种情况的：内嵌结账页设计（`docs/superpowers/specs/2026-11-03-embedded-checkout-design.md` §5.10）写明，要拦「页面套用了优惠，比如首月 $0」和「选错了便宜档」。

## 2. 用户决定

1. 要的是：结账页**自己**显示 0 元时照样开通。系统**不主动**带优惠参数（用户选「只放行 0 元」；主动领优惠有被当成滥用优惠的风险）。
2. 放不放行由后台开关决定（方案 2）：每个订阅套餐、每个地区一个「允许 0 元开通」。默认 Plus 勾上，其余不勾。
3. 注资照旧；关续费后再查一次账号，不是 Plus 就告警；0 元单不算「真实付款跑通」；后台显示 0 元开通。

## 3. 范围

**做：**
- 套餐表加字段和后台开关；
- 下限检查放行 0 元；
- 关续费后复查账号；
- 就绪门槛排除 0 元单；
- 后台金额显示；
- 文档、CHANGELOG、测试。

**不做：**
- 不在建结账会话时加 `promo_campaign` 或任何优惠参数；
- 不放行「0 以上、低于最低金额」的部分优惠（如半价）；
- 点数套餐不支持 0 元；
- 不改注资金额、熔断、确认成功的判据。

## 4. 设计

### 4.1 配置：`RegionConf.AllowZero`

- `payengine/config.go` 的 `RegionConf` 加字段 `AllowZero *bool`，JSON 名 `allow_zero`，带 `omitempty`。注释写明：结账页金额正好是 0 时，是否照常开通。
- 加方法 `func (rc RegionConf) ZeroAllowed() bool`：`rc.AllowZero != nil && *rc.AllowZero`。
- **默认值**：
  - 加 `func zeroAllowedByDefault(planKey string) bool`，只有 `plus` 返回 true。
  - 出厂表（`defaultPlan` / `fillDefaultRegions`）每个地区都写上明确的默认值。
- **读取**（`LoadPlanTable`）：已保存的地区缺这个字段（nil）时，按默认值补上。返回给接口和引擎的值一律不是 nil。
- **保存**（`SavePlanTable`）：
  - 传来的地区缺这个字段（nil）时，沿用当前生效的值：先读当前表，读不到再按默认值。这样还开着旧后台页面的人保存时，不会把手动取消的勾悄悄改回默认值。
  - 有值就按传来的值保存。
- **点数套餐**：`normalizePlan` 一律设为明确的 false，客户端传什么都不采用，和种类、点数由套餐键决定的做法一致。
- 不新增校验报错。允许 0 元时，最低金额仍要大于 0，因为它管的是 0 以上的金额。

### 4.2 放行：下限检查

- **取值**：`createLink` 在取 `j.floorMinor` 的同一处，取 `j.allowZero = rc.ZeroAllowed() && 套餐是订阅`。`job` 加字段 `allowZero bool`，不落库，取值时机和 `floorMinor` 相同。
- **判定**：在 `openPage` 读到金额、币种和上限都检查过之后，把下限检查改成：

  | 情况 | 处理 |
  |---|---|
  | 真实单，`minor == 0` 且 `j.allowZero` | 放行。记 info 事件「支付页显示 0 元（首月免费等优惠），该套餐在该地区允许 0 元开通，照常开通」，`j.note("zero_amount", true)` |
  | 真实单，其他情况 | 照旧：`floorMinor <= 0` 回 `plan_unavailable`，`minor < floorMinor` 回 `amount_below_floor` |
  | 试运行单，`minor == 0` 且 `j.allowZero` | 记 info 事件「…真实付款会照常开通」 |
  | 试运行单，其他情况 | 照旧记 warn 事件「…真实付款会在此放弃」 |

- **读不出、读错照旧**：页面写「Free」「免费」读不出金额的、读到别的数的、币种不符的，都和现在一样放弃，在这一步之前就已拦下。
- **填表后的金额复核**（`pay.go` 的 `recheckAmount`）：不改。0 元填表后还是 0 就通过；变成别的数，照旧以 `amount_changed` 放弃。

### 4.3 注资、点支付、确认成功

- **不改**：
  - 注资按套餐配置的 `FundCents` 注满。卡用一次就注销，钱转回卡池。照旧计入当天的注资金额和笔数。
  - 点支付只点一次。
  - 确认成功仍然只看账号 `plan_type` 是否等于套餐的期望类型。
- **熔断不改**：试用期账号如果不显示 Plus，单子会超时转人工。连续 3 单照旧暂停付款，这道保险不放松。

### 4.4 关续费后复查账号（只对 0 元单）

- **判定 0 元单**：订阅单，`AmountMinor == 0`，并且 `AmountText != ""`（确实读到过金额）。真实单能走到成功，就一定读过金额，并且过了下限检查。
- **复查**：在 `renewal.go` 的 `cancelRenewal` 里，核实续费已关（`renewalOff` 为 true）之后、会话被清空之前，对 0 元单再调一次 `gpt.Account`。期望类型和确认成功时一样，按单据的套餐键从套餐表取 `ExpectPlanType`。
- **结果记在 `job` 上，由调用方处理。续费状态照旧记成已关闭（`cancelled`），单据仍是成功**：

  | 复查结果 | 处理 |
  |---|---|
  | `plan_type` 等于期望 | 记 info 事件「0 元开通的单关续费后账号仍是 Plus」 |
  | 不等于期望 | 记 warn 事件，并告警一次：「付款单 X 以 0 元开通，关闭续费后账号已不是 <期望>（现在是 <plan_type>），可能关续费让优惠当场结束了，请人工处理」 |
  | 账号查询出错 | 记 warn 事件「核实不了」，不告警 |

- **复查只做一次**：关续费的重试、手动重试走到「已经关掉」那条路时也复查。
- **为什么必须关续费**：如果不关，一旦卡被配置成能用多次，下个月 ChatGPT 会从我们的卡上扣原价。所以 0 元单不跳过关续费。

### 4.5 就绪门槛

`db/local_cdk.go` 的 `HasRealSucceededPayOrder`：订阅类条件加 `AND amount_minor > 0`。0 元单成功不能证明真实扣款走得通，不能让发码判定为就绪。点数类不变，点数单没有 0 元。

### 4.6 后台显示

- `frontend/src/views/admin/MarsWallexPay.vue` 列表和详情的金额栏：
  - 读到过金额（有 `amount_text`）且是 0：显示「0.00 USD（0 元开通）」，按币种小数位格式化；
  - 没读到：照旧显示「—」；
  - 大于 0：照旧。
- 实现时确认接口有没有给前端 `amount_text`，没给就补上。
- `frontend/src/views/admin/components/PaySubscriptionPlans.vue` 每个地区一行，加勾选框「允许 0 元开通」，提示：「结账页显示 0 元（首月免费等优惠）时照样开通；不勾则放弃这一单，不注资。」
- `frontend/src/lib/pay.ts`：
  - `RegionConf` 加 `allow_zero?: boolean`，`FormRow` 加 `allowZero: boolean`；
  - `planToForm` 读取；
  - `formToPlan` 对订阅套餐写出 `allow_zero`，点数套餐写 false。
- 点数套餐页（`PayCreditPlans.vue`）不显示这个开关。

### 4.7 文档与 CHANGELOG

- 内嵌结账页设计 §5.10 末尾加一段例外：订阅套餐在某地区勾了「允许 0 元开通」时，页面金额正好是 0 照常开通，见本文。
- `CHANGELOG.md` 新开「未发布」一节，按「升级注意」结构写：
  - **行为变化**：升级后 Plus 默认允许 0 元开通。结账页显示 0 元时照样开通，注资照旧，卡用完转回。不想要的，到后台「卡密与付款 → 自动付款」→「付款配置」取消勾选。
  - **升级后要确认**：刷新开着的后台页面。

## 5. 边界情况

| 情况 | 结果 |
|---|---|
| Plus 勾选，页面 `$0.00` | 放行，注资，点支付，按 Plus 确认 |
| Plus 勾选，页面「Free」（没有数字） | 照旧以 `amount_unreadable` 放弃，没注资 |
| Plus 勾选，页面 `$10.00`（低于最低 $20） | 照旧以 `amount_below_floor` 放弃，没注资 |
| Plus 取消勾选，页面 `$0.00` | 照旧以 `amount_below_floor` 放弃，没注资 |
| Pro（默认不勾），页面 `$0.00` | 照旧放弃 |
| 点数套餐，传来 `allow_zero: true` | 存成 false；0 元照旧放弃 |
| 建会话后、读金额前，管理员改了开关 | 按建会话时取到的值，和最低金额一样 |
| 填表后金额从 0 变成 $20 | 照旧以 `amount_changed` 放弃（已注资的钱随卡回收） |
| 试用期账号不显示 Plus | 照旧超时转人工；连续 3 单触发熔断 |
| 关续费后账号不再是 Plus | 告警，人工处理；单据仍是成功 |
| 0 元单成功 | 不算「真实付款跑通」 |

## 6. 测试

**后端：**
- 下限检查：
  - Plus 允许、0 元 → 不放弃，有 `zero_amount` 记录；
  - Plus 允许、低于最低但不是 0 → `amount_below_floor`；
  - Plus 不允许、0 元 → `amount_below_floor`；
  - Pro 默认、0 元 → `amount_below_floor`；
  - 试运行，允许和不允许各一条事件文字。
- 配置：
  - 出厂默认（Plus true、其余 false、点数 false）；
  - 旧表缺字段时，读取按默认补上；
  - 保存时缺字段，沿用当前值，包括沿用手动取消后的 false；
  - 点数套餐传 true 存成 false；
  - 开关的值在建会话时取。
- 关续费复查：仍是 Plus 不告警；不是 Plus 告警一次；查询出错只记事件；非 0 元单不复查。
- 就绪门槛：只有 0 元成功单时为 false，有一张金额大于 0 的成功单时为 true。

**前端：**
- `pay.ts` 读写 `allow_zero`；
- 订阅套餐页有勾选框；
- 后台金额栏 0 元显示「0 元开通」、没读到显示「—」。

不调用真实业务接口，不动真实资金。

## 7. 上线后才能核实的

代码里核实不了，第一次真遇到 0 元单时看时间线和告警：
1. 真实试用页的金额元素显示什么。如果是「Free」这类没有数字的，照旧放弃，以后再看要不要支持。
2. 首月免费期间，账号接口是不是返回 `plus`。
3. 首月免费期间关续费，是等到期再停，还是当场停掉（4.4 的复查和告警就是为它准备的）。

## 8. 资金与敏感数据

- **资金**：
  - 不新增注资路径，不改注资金额，不新增点击，不放松熔断。
  - 0 元单照旧占当天的注资金额和笔数，钱随卡回收转回。
  - 就绪门槛不让 0 元单当作真实付款的证据。
- **敏感数据**：新增的事件和告警只带单号、套餐类型，不带会话、卡号、邮箱。
